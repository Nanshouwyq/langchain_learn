# note_assistant 踩坑记录

整理自近期开发调试（Agent + RAG + SSE + Moonshot / SiliconFlow）。便于以后对照报错快速定位。

---

## 1. SiliconFlow Embedding 报 `20015`（参数无效）

### 现象

前端 SSE：

```text
正在调用工具：answer_from_notes…
Error code: 400 - {'code': 20015, 'message': 'The parameter is invalid. ...'}
```

容易误判成 **Moonshot 对话参数** 有问题；实际栈在 **建库 / `embed_documents`**。

### 根因

- Embedding 模型 `BAAI/bge-large-zh-v1.5` 上下文约 **512 token**。
- 中文实测大约 **≤500 字** 能过，更长会 20015。
- 曾把 `CHUNK_SIZE` 调到 `900`（为覆盖长笔记），切块超长后 **重建向量库失败**。
- 重建流程是「先 `clear` 再 `create`」：失败后库半残，`build_state.txt` 缺失时下次仍会反复重建 → 每次问答都炸。

### 处理

| 项 | 建议 |
|----|------|
| `CHUNK_SIZE` | `450` 左右（勿盲目加大） |
| `CHUNK_OVERLAP` | `80` |
| `RETEIEVER_K` | 可略加大（如 `8`）补偿小块 |
| Embedding `chunk_size` | 控制批大小（如 `16`），避免单次请求过大 |
| 失败后 | 确认 `vectorstore/build_state.txt` 存在，必要时手动重建成功一次 |

相关：`config.py`、`chains.py` → `get_embedding_model` / `rebuild_vectorstore`。

## 2. Moonshot `kimi-k2.6`：thinking 慢 + 采样参数不匹配

### 现象

- Agent **第一轮 model** 在 LangSmith 里常要 **8～15s**（thinking 默认开，先「想」再出 tool_call）。
- 或 Chat Completions 报 `20015`（`temperature` 与 thinking 模式不一致）。

### 根因（官方约束）

| 模式 | temperature | top_p | 延迟 |
|------|-------------|-------|------|
| thinking 开（API 默认） | 固定 `1` | `0.95` | 首轮偏慢 |
| thinking 关 | 固定 `0.6` | `0.95` | 明显更快 |

`ChatOpenAI` 默认 `temperature=0.7`，对 kimi-k2.6 **非法**，必须按模式显式对齐。

### 处理（当前项目）

`.env`：

```bash
MOONSHOT_THINKING=disabled   # 或 enabled
```

`get_llm()`：`extra_body={"thinking": {"type": ...}}`，并设置对应的 `temperature` / `top_p`。

改完后重启 uvicorn（或等 reload），**新开会话**再看 LangSmith 首轮耗时。

相关：`config.py` → `MOONSHOT_THINKING`；`chains.py` → `get_llm`。

## 3. Agent 流式回答「重复两遍」

### 现象

同一答案先流式出现一遍，结束后又整段再刷一遍。

### 根因

1. 工具内 RAG `stream` 的 token 被 SSE 透出；
2. 工具结束后 Agent **再进 model 复述**一遍；
3. 前端/服务层又对 ToolMessage 整段补发。

### 处理

- `answer_from_notes` / `list_notes` 使用 **`@tool(return_direct=True)`**：工具结果直接作为最终回复，不再二次进 model。
- 写操作（增删改）仍回 model，只做短确认。
- 工具内问答改为 **`invoke`**，避免与外层 `agent.stream` **嵌套双流**抢同一条 SSE。
- `service.agent_chat_stream`：透传工具用 ToolMessage；写操作才跟 model token。

相关：`tools.py`、`agent.py` 图注释、`service.py`。

## 4. Checkpointer 历史不完整 → 下次请求 400

### 现象

上一轮中断 / 流式异常后，再聊同一 `session_id` 报错（工具相关 400），类似「有 `tool_calls` 却没有对应 `ToolMessage`」。

### 根因

LangGraph `InMemorySaver` 留下 **半截 AIMessage(tool_calls)**，下一轮拼进 messages 发给模型/API，协议不合法。

### 处理

- `before_model` 中间件：`repair_orphaned_tool_calls` 补假 `ToolMessage`。
- 调用前 `repair_thread_state(agent, config)`。
- 调试时换新 `session_id` / 清会话最省事。

相关：`agent.py` → `missing_tool_messages` / `repair_thread_state`。

## 5. RAG 答不全（长笔记只覆盖开头）

### 现象

问 FastAPI 等长文，只答到笔记前几节。

### 根因

- `CHUNK_SIZE` 过大时检索块少且碎；或过小 + `k` 太低 → Top-K 盖不住全文。
- Prompt 过度强调「简洁」会丢掉细节。

### 处理

- 在 **Embedding 上限内** 取合理 `CHUNK_SIZE`，适当提高 `RETEIEVER_K`。
- Prompt 要求：相关片段尽量完整引用、分点覆盖多小节。
- 改切分后要 **重建向量库**（删 `build_state` 或调 `rebuild_vectorstore`）。

注意：加大 chunk **必须服从第 1 条**，否则建库直接 20015。

## 6. 问答偏慢（多轮 LLM）

### 现象

一次「基于笔记回答」要等很久。

### 根因链路

1. Agent model 决策工具  
2. （可选）查询改写又一次 LLM  
3. RAG 生成答案  
4. Agent 再总结（未 `return_direct` 时）

可能 **3～4 次** 模型调用。

### 处理

| 手段 | 说明 |
|------|------|
| `ENABLE_QUERY_REWRITE=False` | 日常默认关，少 1 次 LLM |
| 缓存 LLM / Embedding / RAG 链 | 避免每次重建 |
| `return_direct` | 去掉二次复述 |
| 纯问答走 `/rag` | 跳过 Agent 决策轮 |

## 7. uvicorn `--reload` 用到旧模型 / 旧 Agent

### 现象

改了 `temperature` / 工具定义，行为仍像旧代码。

### 根因

模块级单例 `_llm`、`_agent`、`_rag_chain` 在部分 reload 路径下未清干净。

### 处理

- `service` 导入时调用 `reset_llm_clients()`。
- 仍异常则手动停掉再启 uvicorn，前端新开对话。

## 8. 评测用例不能直接丢进 LangGraph / LangSmith

### 现象

本地 `eval/eval_cases.json` 想「导入 LangGraph」。

### 说明

- LangGraph **不吃**这套自定义 JSON。
- 评测数据集在 **LangSmith**：需要 `inputs` / `outputs` 结构。

### 处理

```bash
# 本地规则打分
python -m note_assistant.eval.run_eval
python -m note_assistant.eval.run_eval --type agent

# 同步到 LangSmith Dataset（默认名 note-assistant-eval）
python -m note_assistant.eval.upload_langsmith
python -m note_assistant.eval.upload_langsmith --replace
```

本地字段 `must_include*` 会进 example 的 `outputs`，`question` / `type` 进 `inputs`。

## 9. 其它零散问题（简记）

| 问题 | 要点 |
|------|------|
| Python 缩进不一致 | 同级必须统一空格数（曾踩在 `list_notes`） |
| 流式里「思考 + 最终答案」粘在一起 | 工具调用后重置回复缓冲（`reset` 事件） |
| 前端按钮图标文字不齐 | flex / 行高，别只靠 AntD 默认 |
| Markdown 渲染 | `markdown-it` + DOMPurify；注意装依赖时别弄坏 `package.json` |
| `__pycache__` 干扰热更 | 可配合 `PYTHONDONTWRITEBYTECODE` / 清缓存 |
| SiliconFlow Embedding | 第三方接口建议 `check_embedding_ctx_length=False` |

## 10. 延迟瓶颈（LangSmith trace）

典型一次 Agent 问答：

| 环节 | 量级 | 说明 |
|------|------|------|
| `model`（选工具） | 3～10s | thinking 开会更慢 |
| `answer_from_notes` / RAG `ChatOpenAI` | **30～90s** | 主瓶颈：上下文长 + 长文生成 |
| 检索 | ~1s | 通常可接受 |

已做优化：

1. `MOONSHOT_THINKING=disabled`
2. 知识问答 **短路直连 RAG**（`ENABLE_RAG_SHORTCUT`），跳过首轮 model
3. `RETEIEVER_K=4` + `CONTEXT_MAX_CHARS` 截断
4. 精简 RAG prompt + `RAG_MAX_TOKENS` / `AGENT_MAX_TOKENS`
5. Agent / RAG 分用途 `get_llm(purpose=...)`

导出对比：`python -m note_assistant.eval.export_traces --limit 5 --days 1 --no-io`

## 排查口诀

1. **先看报错栈**：20015 在 `embeddings` 还是 `chat.completions`？  
2. **建库是否刚失败**：有没有 `build_state.txt`、Chroma 是否空？  
3. **Agent 是否二次生成**：透传工具有没有 `return_direct`？  
4. **会话是否脏**：换 `session_id` 再试。  
5. **参数是否厂商锁定**：kimi thinking / BGE 长度不要想当然。
